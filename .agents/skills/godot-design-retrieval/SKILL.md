# Finding and using design

`docs/design/` grows. Reading all of it is affordable at three sections and
impossible at fifty. Retrieval is therefore a first-class step, not something
done by loading the folder.

## Always start at the index

`docs/design/INDEX.md` is generated by `tools/design.py` and holds one line per
section: title, resolution, and what it is about.

Read the index. Choose the sections that matter. Open only those.

Do not read the whole design body. Do not read a section because it sounds
adjacent. Two or three sections is a normal working set for a slice.

The index also carries a cross-reference graph, so if a section says it is
constrained by another, follow that link rather than guessing which other
sections might apply.

## Folder structure

One concern per file, grouped by the kind of concern:

```
docs/design/
  INDEX.md              generated, do not edit
  README.md             how design works in this repo
  experience/           the fantasy, session shape, what a player is doing
  world/                setting, scale, structure, traversal
  interaction/          controls, camera, movement feel, feedback
  systems/              combat, progression, economy - one file each
  content/              what content exists, who authors it, how it is validated
  presentation/         visual language, audio, readability, accessibility
  social/               multiplayer shape, authority, moderation
  boundaries.md         what this game is deliberately not
```

Folders appear when there is a second file that belongs in one. A single file
about movement lives at `interaction/player-movement.md`; it does not need
`interaction/` to exist first as an empty gesture.

Depth beyond two levels usually means a file is trying to cover several
concerns. Split it rather than nesting further.

## Tunables

A design section states which values are adjustable, and what range still feels
right. It never states where they live in code.

Design declares:

```markdown
## Tunables

| Tunable | What it controls | Range that still feels right |
|---|---|---|
| `movement.max_speed` | Peak horizontal speed | 260 to 380 |
```

Code claims:

```gdscript
## @tune movement.max_speed
## Peak horizontal speed. Above 380 it starts to feel floaty.
@export var max_speed: float = 320.0
```

`tools/design.py` then generates a table inside the design section showing the
current value, where it is set, and that comment. The design document contains
no path, so code is free to move.

Three rules:

**Declaring a tunable is a requirement that it be adjustable.** A `const` cannot
be changed without a rebuild, so binding a design-declared tunable to one is
reported. Prefer `@export`, which is also inspector-editable.

**A tunable claimed in code that no section declares is reported.** That is a
knob nobody designed. Either declare it, or inline the value because it was
never meant to be tuned. This is the more useful signal of the two: a magic
number invented during implementation surfaces here rather than being noticed by
eye three sessions later.

**Never copy a value from code into design.** The range belongs in design; the
value belongs in code and is generated into the document. A number in both
places means one is wrong and nobody knows which.

## Deriving the next slice from design

When the human has not asked for anything specific, the next work is derivable.
`docs/design/INDEX.md` has a "Ready to work on" section listing:

- **Settled, nothing bound.** Design is decided and no code claims its tunables.
  Straightforwardly unbuilt.
- **Settled, partly bound.** Some tunables claimed, some not. Finish it.
- **Open question with a stated way to settle it.** The section says what would
  answer it. That is a probe, not a feature: build the smallest thing that
  produces the answer.
- **A leaning, not committed.** Needs confirming or ruling out.

This is derived from resolution and binding state, not a stored backlog. There
is no task list to keep in sync, and nothing to go stale.

Offer candidates and let the human choose. Do not silently pick one and start
building - the choice of what to work on next is theirs, and the derivation only
tells you what is available.

Once chosen, the section is what the proposal cites in `design_refs`, and its
constraints are what the work must respect.

## When the design body cannot answer

If the index has no section covering the work, that is not a gap to paper over.
It means the work has no stated purpose yet, and the honest move is discovery
rather than a rationale reasoned up from the feature itself.

See `godot-design-discovery`.
