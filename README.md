# Godot Agent Starter

Agent-ready Godot **4.7.1** project skeleton. GDScript only, cross-platform.

Genre-agnostic. It does not assume multiplayer, 3D, procedural content or a custom
level format. Every game-shaped choice is a deletable file or a documented decision,
not a baked-in assumption.

The point of this repo is not the game code. It is the scaffolding that makes an AI
agent's output **verifiable**: strict type enforcement, a gate script that does not
trust Godot's exit codes, and a written contract for what the agent may and may not
touch.

## Start here

Open a terminal in this folder, start your coding agent, and say **"let's begin"**.

The agent reads `SETUP.md`, detects what is missing, installs and configures
everything it can, and asks you only for the one thing it cannot do itself:
downloading Godot. There is no human checklist.

To see the state of your machine without an agent:

```
python bootstrap.py          # what is missing
python bootstrap.py --fix    # do everything automatable
```

### Documents

Deliberately layered: the two files an agent loads at session start are short, and
everything else is reference material pulled in on demand.

**Loaded at session start**

1. **[AGENTS.md](AGENTS.md)** — the contract, kept short enough to land in one read.
2. **[SETUP.md](SETUP.md)** — the setup runbook the agent executes.

**Retrieved on demand by the agent itself**

- **[.agents/skills/](.agents/skills/)** — nine Godot skills. Only the `name` and
  `description` load at startup (~100 tokens each); the agent pulls in a body when it
  hits a domain it is unsure about. Failing gate stages name the relevant skill.

**Reference, on demand**

3. **[docs/GATE.md](docs/GATE.md)** — every stage and how to fix each failure.
4. **[docs/RULES.md](docs/RULES.md)** — full ownership table, banned idioms, concurrency.
5. **[docs/SCENES.md](docs/SCENES.md)** — writing `.tscn` and `.tres` safely.
6. **[docs/GDSCRIPT.md](docs/GDSCRIPT.md)** — strict-mode idioms, generated from real code.
7. **[docs/WORKFLOW.md](docs/WORKFLOW.md)** — the day-to-day loop.
8. **[docs/DECISIONS.md](docs/DECISIONS.md)** — every choice, and how to reverse it.
8. **[ARCHITECTURE.md](ARCHITECTURE.md)** — generated module graph.

## The living plan

Open **`plan.html`** in a browser. It is the one page that shows where the
project stands:

| Section | Source | Meaning |
|---|---|---|
| Building now | `proposal.json` + the real tree | Proposed structure, with per-file state: built, to do, or **unproposed** |
| Slice hierarchy | `proposal.json` + `arch.py --json` | A diagram from `src/` down to functions, coloured green (built as approved), amber (approved, not written), red (exists without approval) |
| Open questions | `project.shape.json` `questions[]` | The frontier -- what is blocked on a decision |
| Why this work exists | `proposal.json` `design_refs[]` | The design section this slice descends from |
| Direction | `direction[]` | What today's work must leave room for. Not a backlog. |
| How the plan changed | `proposal.json` `revisions[]` | Each deviation, and what building it revealed |
| Settled | `decisions[]` | Append-only ledger, superseded entries dimmed |
| Actual architecture | `arch.py` | The module graph derived from code |
| Recent changes | git | Commits with links into the tree |
| Game design | `docs/design/` | What the game is. Rendered inline, click to expand |
| How the kit works | `docs/` | The gate, the rules, the workflow. Rendered inline |

It is **generated** -- the gate rewrites it on every run, so it cannot be
stale. Never edit it; edit `project.shape.json` or `proposal.json` and rerun.

### Two kinds of documentation

`docs/` is about the kit. `docs/design/` is about the game. They are separate
because they answer different questions and change at different rates, and
because a reader looking for the visual language should not have to wade through
gate remediation.

**How design works is documented once, in `docs/design/README.md`.** That covers
resolution levels, why design precedes code, where sections come from, and the
relationship to the decision ledger. It is not repeated here.

Both folders render inline in the page as collapsible sections, including any
mermaid diagrams inside them. Documents are pre-rendered at generation time
rather than fetched, because `file://` forbids `fetch()` -- a page opened by
double-clicking cannot load a sibling `.md` at all.

Diagrams need `tools/vendor/mermaid.min.js`, which `bootstrap.py --fix`
downloads. Vendored rather than loaded from a CDN so the page works offline and
behind a proxy. Without it, diagrams show as readable source text.

`python tools/plan_html.py --slice slice-2` also writes `plan/slice-2.html`.
Those snapshots are the point: when a slice goes wrong, open the snapshot from
when it started next to the current plan and see where the design turned.

### Talking about the plan (optional)

The page is plain HTML with no dependencies, so double-clicking it works. If
you want to annotate it and have the agent read your comments, run
[Lavish](https://github.com/kunchenguid/lavish-axi):

```
npx -y lavish-axi
```

It wraps the file in an iframe and adds highlighting, comments and a chat that
the agent polls. It does not own the file -- the saved HTML renders identically
with or without it, so this is an optional upgrade, not a dependency. Nothing
in the gate touches it. Note it binds loopback by default; check that before
running it on a work machine.

## The gate

```
python check.py                    # all stages
python check.py --only typecheck   # one stage
python check.py --fast             # skip import
python check.py --list             # show stage names
```

`integrity` -> `format` -> `lint` -> `sanitise` -> `import` -> `typecheck` -> `grep`
-> `arch` -> `assets` -> `resources` -> `gut` -> `smoke`.

It greps output rather than trusting exit codes, because Godot's are unreliable in both
directions: `--import --quit` can exit 1 on a clean import, and other commands exit 0
while printing hard errors. Errors are checked on every branch, including success paths:
GUT will happily print "All tests passed!" and a `[GUT ERROR]` in the same run.

## The three rules that matter most

**Ownership by operation, not by extension.** The agent owns `.gd`, `.gdshader`, tests,
docs, **and scenes**, because the `sanitise` and `resources` stages verify scenes to the
same standard as everything else. It never touches `.import`, `.uid`, `src/project.godot`,
`export_presets.cfg`, or the gate itself. Graph-authored resources (AnimationTree,
TileSet terrain, visual shaders) and bakes stay yours because their text form has no
meaningful authoring semantics.

Concurrency is the real constraint, not permission: Godot does not lock files and never
reloads an open scene from disk, so **close the editor or put the agent in a
`git worktree`.** That applies to `git pull` just as much as to an agent.

**The gate is tamper-evident.** `check.py`, `arch.py`, `sanitise.py`, `src/project.godot` and the rule
files are hashed into `.gate.sha256`, checked before any other stage. Editing
the gate to make a failure disappear is the one prohibited act, and the tripwire shows
up in the diff. Re-baselining needs an explicit `--accept-gate-changes`, which the deny
list forbids the agent from running.

**Architecture.** Game logic goes in plain `RefCounted` classes under `src/scripts/logic/`
with no scene dependency. That code the agent can write and verify entirely on its own.
Node-dependent code it cannot verify at all. `src/scripts/logic/health.gd` is the example.

**No second source of truth.** The module graph in `ARCHITECTURE.md` is generated from
the code by `arch.py`, and the gate fails if the committed copy is stale. Allowed
dependencies live in `arch.rules.json` and are enforced from the same graph. A
hand-maintained architecture doc drifts within weeks; a generated one cannot.

## Tailoring it to your game

| Want | Do |
| --- | --- |
| Single-player | Delete the `net`-tagged rules from `gate.rules.json`, drop the multiplayer section of `docs/RULES.md` |
| Hand-authored levels only | Delete `src/scripts/data/level_format.gd` and its test |
| 2D | Change the renderer in `src/project.godot`, note it in `docs/DECISIONS.md` |
| Deeper directory tree | Raise `module_depth` in `arch.rules.json` |
| A new module | Add it to `arch.rules.json` with its allowed dependencies, then `python arch.py --write` |
| Feature folders instead of layer folders | Set `type_boundary.interior` / `.boundary` in `arch.rules.json` to your layout; no gate file needs editing |
| No decision log | Delete `project.shape.json`; the `shape` stage skips and agents ask instead |
| Skip the multiplayer skill | `rm -r .agents/skills/godot-multiplayer-authority` and drop its row from `AGENTS.md` |

Unlisted modules are drawn but not constrained, so you can restructure freely and
tighten the rules afterwards.

**`project.shape.json` is an append-only decision log.** Onboarding asks two things:
the project name, and one or two sentences on what the game is. Bootstrap reports
`MANUAL` until those exist. Nothing else is ever demanded up front — a new project cannot
honestly say how many entities update per frame or whether content will be player-made,
and a gate that insists gets a fabricated answer that every later agent trusts.

Everything else is recorded as it is settled, with the question, the answer, who decided,
and one line on what forced it. Two rules fill the log: an agent raises a fork rather than
picking it, and appends anything settled in passing. A decision is anything that would make
a later agent act differently, so art direction, scope, audience, monetisation and
moderation qualify as much as entity counts — there is no category list. Placeholder
answers (`unknown`, `tbd`) are rejected by the `shape` stage: an undecided question is an
absent entry, and a fabricated one is worse than none.

The log covers technical direction, not product planning. If you want a process for
deciding *what to build next*, [wayfinder](https://www.aihero.dev/skills-wayfinder) does
that well and complements this — append anything it resolves that constrains code. It is
not a dependency.

No C++ or GDExtension, no ECS, no MCP, no CI, no export presets, no editor plugin,
no screenshot capture. Add them when a profiler or a specific need justifies it, not
up front. `docs/DECISIONS.md` records why each was left out and what would change the
answer.
